# Mentor Operations Registry

<!-- upstream-pin: 0.16.0 -->
<!-- mentor-mcp-surface: session-based, measured live 2026-09-02 -->

**Surface note (measured live 2026-09-02):** the Mentor tools are session-based. `mentor_start`,
`mentor_cancel`, `publish_start` and `mentor_get_event` are no longer exposed by the server. The
sequence is `mentor_start_session()` -> `mentor_load_asset` / `mentor_create_asset` ->
`mentor_prompt` -> `mentor_get_run` -> `mentor_publish` -> `publish_status` ->
`mentor_close_session`. One asset per session, one run at a time (a second `mentor_prompt` while a
run is in flight is silently ignored). Tiering is unchanged; only the names and the cursor rule
moved. Rows below name the current tools; the old names appear only where a row pins pre-2026-09
evidence.

Rule (adapted from an internal OutSystems team's service-registry pattern, mirroring
`odc-error-registry.md`): this registry is the canonical INDEX of Mentor and
OutSystems-MCP operation cadence — one row per operation (or tier-grouped
operation family), giving its polling tier, poll cadence, typical duration,
cancel guidance, and a session-economics note. Skills resolve an operation's
cadence here first. `outsystems-mentor-polling-behavior` (not part of the colleague sprint-loop pack) is the
owning skill for tier definitions, cadence values, and drain/pause mechanics
and keeps the full treatment; where that skill is not installed, the row here
is the whole answer. Adding a competing cadence explanation to a file that is
not the owner, or letting a row drift from the owner's text, is a lint
finding.

| Operation | Tier | Poll cadence | Typical duration | Cancel guidance | Session-economics note |
|---|---|---|---|---|---|
| Tier 1 read/query tools: `app_list`, `app_info`, `app_refs`, `env_list`, `env_apps`, `context_screens`, `context_entities`, `context_actions`, `context_roles`, `context_structures`, `context_themes`, `context_search` | Tier 1 (sync) | No polling — call once, use the result immediately; no sleep, no cursor, no retry loop. | Synchronous / immediate. | Not applicable — no async run exists to cancel. | Zero poll cost by design; never add a sleep or poll loop before using these tools' results, and never apply Tier 3 sleep discipline to them. |
| Tier 2 async tools: `mentor_publish` → `publish_status` (pass the returned `publicationKey` as `publish_key`); `deploy_start` → `deploy_status`; `extlib_upload` → `extlib_status`; `test_setup_start` → `test_setup_status` | Tier 2 (fast async) | ~15s between status checks (upstream 0.16.0 still scopes these OUT of the mentor rule and accepts 5–15s where a tool's own description gives no cadence; this catalog defaults to the token-lean 15s end); never poll faster than 5s, and never SLOWER than 15s. The upper bound is the one agents break: sleeping 45–90s on a publish poll (measured 2026-08-23, three publishes) hides a terminal state that arrived inside a ~2 min build, and Tier 2 responses are a status string and a key, so the tokens saved by a longer sleep are negligible against the latency added. | Typically 30–90s. | None of this registry's sources name a cancel tool for these operations — no cancel guidance is documented for Tier 2 runs. | Intermediate poll responses are compact (a status string and a key), so frequent polling costs little in tokens; still, don't apply Tier 1's no-sleep behavior here (hammering `publish_status` etc. without sleep burns tokens on frequent-but-compact responses), and don't apply Tier 3's 30s pause either — Tier 2 completes faster and a 30s wait is needlessly slow. |
| Mentor authoring run: `mentor_prompt` → `mentor_get_run(sessionId, runId)` (the only Tier 3 tool) | Tier 3 (long async / verbose) | Drain-then-pause: poll immediately after `mentor_prompt`, and again immediately while events keep arriving (events are batched — draining is correctness, not token waste). Pause ~30s (`tier3CadenceSecs`) only once a poll returns no new events and `status` is non-terminal. **Omit the cursor on every poll, first and subsequent** (measured 2026-09-02): a bare poll returns only events not yet delivered, and a cursor is a deliberate *re-read* control (a previous `nextCursor`, or `0` for the whole history), so passing the previous cursor back re-delivers events already in context. `outsystems-mentor-polling-behavior` still says to always pass it; the server's `mentor_get_run` description contradicts that and the description wins (quoted verbatim in `../../outsystems-mentor-implementation/references/execution-gates.md` §4d). Stop at `succeeded` / `failed` / `cancelled` / `not_found`, when `nextCursor` is absent and `hasMore` is false — a terminal poll carries no `nextCursor` and no `pollIntervalMs` key at all. | `outsystems-mentor-polling-behavior`: runs typically take 2–10 minutes (~8–15 polls at the 30s drained cadence). OMI field measurement (`execution-gates.md`): healthy small turns reach terminal in 1–5 min; heavy structural turns legitimately run 8–12 min with ~7 quiet minutes being normal — judge "stuck" against the turn's size, not a flat timer. | `mcp__outsystems__mentor_cancel_prompt(sessionId, runId)` — cancels only the session's *current* run (any other `runId` is a no-op) and **leaves the session open**, so it is not a teardown: call `mentor_close_session(sessionId)` when the sequence actually ends. Fire-and-forget — poll once after to confirm `cancelled`, then stop (`outsystems-mentor-copilot`). Give a heavy turn ~12–14 min before considering cancel, and only cancel if you also intend to split the work smaller — a cancel that re-runs the same oversized prompt buys nothing. Cancel costs >3 min to settle, a cancelled turn commits nothing (failed/cancelled turns never advance OML), and cancelling an already-succeeded run is a no-op you will misread as a wedge — re-poll the `runId` before concluding anything (`execution-gates.md`). Hang tell: a `nextCursor` unchanged for ~7–10 minutes is the cursor-side signature of a wedge; one `details: true` poll confirms before applying the cancel calibration above. | ~8–15 polls at the drained 30s cadence vs ~240–600 polls at the server's 500ms `pollAfterMs` hint — 30–40× more tokens (`outsystems-mentor-polling-behavior`). Real field runs (`outsystems-mentor-copilot`, `morpheus-qa` tenant): 3 polls / ~30K tokens for a warm-cache `doc-gap-fill`; 11 polls / ~300K tokens for a cold-cache `demo-readiness` run, dominated by one 30–500KB `tool_end` OML-scan event that lands once and is re-read as cache on every later turn. A poll loop past ~20 iterations with no terminal state signals an over-broad prompt — cancel and narrow scope rather than continuing to poll. Lengthening the drained pause is a real lever on poll count (that is what `tier3CadenceSecs` configures) — but it is a TRADE, not a free saving, and the cost lands on wall-clock: a longer pause buys fewer status polls and pays for them with later observation of a terminal state that may already have arrived. Price both sides before lengthening it, and never lengthen it silently past the served value on the assumption that only tokens are at stake (measured 2026-08-23: 75–150s pauses against a served 30s bought a handful of polls and cost minutes of latency across four authoring turns and three publishes, which the operator read as unacceptable). When elapsed time is what a human is waiting on, sleep the served value. Upstream plugin 0.16.0 now states this as one rule with a floor — sleep the interval the poll advertised, and at least ~30s, because each poll costs a whole model turn, so a sub-second figure early in a run is not worth chasing while a figure longer than 30s is and wins — which supersedes the older competing "~30s reference" wording the same release removed. Either way the pause is dead time for the model only — move independent work into it rather than serialising that work after the run. |
